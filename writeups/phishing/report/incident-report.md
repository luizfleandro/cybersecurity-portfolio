# 1. Executive Summary

An Android device displayed notifications impersonating CAIXA (Caixa Econômica Federal), using CAIXA branding and the message:

> "Novidade para você! Produto especial para clientes VIP!"

The notification linked to:

`hxxps://caixa[.]braz[.]lat/?gaid=<REDACTED>`

A second, expanded form of the URL was later observed with an additional parameter (`bnm_cid=<REDACTED>`). See Section 2.2 for where and how it was observed.

The domain presented a page impersonating a Google Play application listing with CAIXA branding. The page title was `CAIXA - Apps on Google Play`, and the page referenced Google-hosted images, Google Analytics, Google Tag Manager and Google reCAPTCHA resources.

Passive investigation showed the domain is served through Cloudflare. On VirusTotal, **6 of 90 vendors flagged the URL as malicious** (including a *Phishing and Other Frauds* verdict), while other vendors provided non-malicious categorizations (*dynamic content*, *financial_services*).

The link was opened once on the affected device during initial observation. No application was installed, and no credentials, banking data or authentication data were submitted. All subsequent analysis was passive.

The evidence supports classifying the infrastructure as **suspected phishing / brand impersonation infrastructure**. It does not establish the operator's identity, the origin server behind Cloudflare, or the source of the original notification.

# 7. Certificate Transparency

A query for `%.braz.lat` against `crt.sh` returned **no records**.

**Assessment:** this result is treated as a **query/coverage limitation, not as evidence of absence**. The site is served over HTTPS with a browser-accepted certificate, and publicly trusted certificates are expected to be logged in CT. An empty result therefore most likely reflects a failed or incomplete lookup (crt.sh is known to time out or return partial results).

Required follow-up (tracked in Section 18):

* Repeat the crt.sh query using the exact name `braz.lat` and `caixa.braz.lat`.
* Cross-check with at least one other CT source (e.g., Censys, Certspotter).

**Attribution caveat:** VirusTotal recorded the *final URL* of its browser session as a Google reCAPTCHA endpoint. The HTTP fields above (status, content type, body length, serving IP) are therefore recorded against that final request and **may not describe the response from `caixa[.]braz[.]lat` itself**. The HTML title and metadata in Section 11 are attributed by VirusTotal to the analyzed page. Which request each field belongs to is listed as an open item in Section 18.


**Note on `br.com.gabba.Caixa`:** this identifier is *believed* to correspond to the official CAIXA application, but this has **not been verified** against the public Play Store listing. Verification is a passive check and is scheduled in Section 18. If confirmed, the page most likely reproduces legitimate listing metadata rather than promoting a rogue package. That would be consistent with a cloned page and with possible cloaking (H4), and would make the actual payload path (if any) an open question.

The page also referenced Google Tag Manager, Google Analytics, Google-hosted images, Google reCAPTCHA and Google Play resources.

### Assessment

The title, `@GooglePlay` metadata and Play-style presentation show the page was designed to look like a CAIXA listing on Google Play.

### Important distinction

Use of legitimate Google infrastructure does **not** mean Google operates or endorses the domain. Any website can embed or reference third-party resources.

# 14. Investigation Hypotheses

## H1 — CAIXA brand impersonation

**Status:** Strongly supported.

Evidence: CAIXA branding and icon in the notification; `caixa` in the domain; page title impersonating a CAIXA listing on Google Play; Play-style presentation on a non-official domain.

## H2 — Phishing or fraudulent application distribution

**Status:** Supported, under investigation.

Evidence: multiple malicious vendor verdicts including a phishing/fraud classification; unsolicited notification; brand impersonation; Play-style page on a non-Google domain.

Gap: the attack chain is not established, including whether an APK or credential-harvesting form is served.

## H3 — `142.251.155.119` is attacker infrastructure

**Status:** Rejected.

Reason: WHOIS identifies Google LLC; the address corresponds to the reCAPTCHA request recorded as the final URL; current DNS for the domain resolves to Cloudflare.

## H4 — Cloaking / scanner evasion

**Status:** Open, plausible, untested.

Rationale: the page metadata may mirror a legitimate Play listing, and a security scanner may have received different content than a real victim would. The site may vary content by User-Agent, geography or parameters. Testing requires Phase 2.

## H5 — Advertising-driven scam funnel or adware-originated traffic

**Status:** Open, untested.

Rationale: the `gaid`-style parameter and the "VIP product" message are consistent with ad-tech tracking. The campaign may be a scam or affiliate funnel rather than (or in addition to) targeted phishing. Determining the notification's source is required to assess this.

# 19. Next Investigation Phase

**Phase 1b — remaining passive steps** (Section 18), followed by **Phase 2 — controlled active analysis**.

Preparation before any direct interaction:

1. Prepare an isolated VM with a clean snapshot.
2. Disable shared folders, clipboard integration and drag-and-drop.
3. Use network egress not tied to personal infrastructure (e.g., dedicated VPN or cloud VM).
4. Avoid personal accounts and sensitive information.
5. Record timestamps and preserve all command output.

Because the site may cloak (H4), first consider a sandboxed scan via urlscan.io with Brazilian geolocation and a mobile User-Agent before touching the site directly. Any direct request from a desktop client outside Brazil may return decoy content.

Planned sequence:

```text
HEAD request
    ↓
TLS certificate inspection
    ↓
Controlled GET (with and without mobile UA)
    ↓
Preserve headers + HTML
    ↓
SHA-256 hashing of collected files
    ↓
Offline HTML analysis
    ↓
Redirect / script / iframe analysis
    ↓
Controlled browser analysis only if justified
```

No APK installation, credential submission, exploitation, vulnerability scanning or aggressive probing is planned.

# 21. Investigation Principles

* Passive analysis before active interaction.
* Minimum necessary interaction with suspected infrastructure.
* Evidence preservation before interpretation.
* Separation of observed facts, analysis and hypotheses.
* No installation of potentially malicious software on the analyst's primary system.
* No submission of credentials or sensitive information.
* No exploitation or unauthorized access.
* Third-party infrastructure is not classified as malicious without supporting evidence.
